## 1. Проблема и цель

Сейчас в приложении есть ровно одна ступень доступа: «вошёл — можно всё».
Единственная проверка — `LoginRequiredMixin` в представлениях, отдельной модели
ролей и прав нет. Поэтому любой аутентифицированный пользователь может создать,
изменить и удалить любое пиво, любой хмель и любого производителя, а чужие
оценки открываются и правятся по прямому URL.

Последствия серьёзнее, чем «неудобно»: удаление пива каскадно удаляет все оценки
всех пользователей этого пива (`brewery/models.py:120-121`), корзины и
восстановления нет. Одна ошибочная или злонамеренная правка уничтожает общий
каталог и историю оценок без возможности отката средствами интерфейса.

Пока пользователей заводит администратор через `/admin/`, круг «тех, кому можно
всё», совпадает с кругом доверенных людей. С появлением входа через внешнего
провайдера (BL-09) этот круг становится публичным: доступ к каталогу получит
любой владелец аккаунта Yandex. Это делает разграничение прав обязательным
условием безопасного включения соцвхода.

**Цель:** права в приложении определяются ролью — гость, пользователь,
администратор — каталог изменяют только администраторы, оценки — только их
владелец, и все эти ограничения проверяются на сервере и покрыты тестами.

## 2. Область

### Входит в область

- Роли: гость (без сессии), пользователь (аутентифицирован, `is_staff=False`),
  администратор (`is_staff=True`).
- Матрица доступа: кто и что может делать в разделах «Пиво», «Хмель»,
  «Производители», «Оценки», «Отчет», на главной.
- Каталог (пиво, хмель, производители): просмотр — всем вошедшим, создание,
  изменение и удаление — только администраторам.
- Оценки: создание — любому вошедшему, изменение и удаление — только владельцу.
- Интерфейс: кнопки и ссылки, ведущие к недоступным действиям, не показываются.
- Ответы на отказ: коды 403 и 404, русские тексты для 403, запись в лог.
- Тесты на каждый критерий приёмки.
- Состав администраторов: после выката `is_staff = True` остаётся только у
  пользователей `admin` и `qqmax7`, у всех остальных — `False`.

### Не входит (Non-goals)

- Регистрация, вход через внешних провайдеров и приглашения — BL-09.
- Серверная валидация `score` 1–10 — BL-01, остаётся там.
- Появление автора (владельца) у пива, хмеля и производителя и раздел «мои
  записи» — отдельная спека, если понадобится.
- Отдельная роль «редактор каталога без доступа в админку»: сейчас
  администратор каталога — это `is_staff`, а он же имеет доступ к `/admin/`.
- Модерация, журнал аудита изменений каталога, корзина и откат удаления.
- Уникальность оценки `(beer, owner)` — BL-02.
- Переопределение стандартной страницы 404 и локализация системных ошибок,
  кроме 403.
- Ограничение доступа к файлам в `media/` (их отдаёт Caddy без проверки входа).

## 3. Роли и сценарии

- **US-01.** Как гость, я хочу открыть главную и попасть на страницу входа,
  чтобы понять, что для работы с базой нужен аккаунт.
- **US-02.** Как пользователь, я хочу смотреть каталог и ставить свои оценки,
  чтобы вести личный список впечатлений и не бояться, что кто-то испортит
  общий каталог.
- **US-03.** Как пользователь, я хочу быть уверенным, что мои оценки и
  комментарии не может изменить никто другой.
- **US-04.** Как администратор, я хочу добавлять и исправлять пиво, хмель и
  производителей, чтобы база оставалась актуальной.
- **US-05.** Как администратор, я не хочу, чтобы кнопки и ссылки предлагали
  действия, которые всё равно закончатся отказом.

## 4. Функциональные требования

Формулировки — наблюдаемое поведение. Приоритеты: MUST / SHOULD / MAY.

- **FR-001 (MUST). Роли.** Администратором считается пользователь с
  `is_staff = True`, пользователем — любой другой аутентифицированный
  пользователь, гостем — пользователь без сессии. Отдельных полей и групп не
  вводится; роль меняется в `/admin/`.
- **FR-002 (MUST). Матрица доступа.**

  | Раздел / действие | Гость | Пользователь | Администратор |
  |---|---|---|---|
  | Главная `/` | да | да | да |
  | Пиво, хмель, производители: список и карточка | нет, редирект на вход | да | да |
  | Пиво, хмель, производители: создание, изменение, удаление | нет, редирект на вход | **нет, 403** | да |
  | Оценки: список `/ratings/` | нет, редирект на вход | только свои | только свои |
  | Оценки: создание | нет, редирект на вход | да | да |
  | Оценки: изменение и удаление | нет, редирект на вход | только свои, чужая — 404 | только свои, чужая — 404 |
  | Отчет `/reports/` | нет, редирект на вход | да | да |
  | `/admin/` | нет | нет | да |

- **FR-003 (MUST). Каталог — только администратор.** Запрос от пользователя без
  `is_staff` на создание, изменение или удаление пива, хмеля и производителя
  завершается ответом 403; данные в базе не меняются. Администратор выполняет
  те же действия как раньше: после успешной операции возврат на список раздела,
  удаление — через страницу подтверждения.
- **FR-004 (MUST). Просмотр — всем вошедшим.** Списки и карточки каталога и
  страница «Отчет» доступны любому аутентифицированному пользователю
  независимо от роли.
- **FR-005 (MUST). Оценки — только свои.** Пользователь создаёт оценку, и её
  владельцем становится он сам. Изменять и удалять он может только оценки со
  своим владельцем. Оценка другого пользователя при обращении по прямому URL
  отвечает 404 — и для обычного пользователя, и для администратора (админ
  правит такие оценки в `/admin/`, где inline оценок уже есть). Оценка без
  владельца (`owner IS NULL`) через веб-интерфейс недоступна никому.
- **FR-006 (MUST). Интерфейс не обещает недоступного.** Кнопки «Добавить …» и
  ссылки «Изменить» / «Удалить» в разделах каталога видны только
  администратору; ссылки «Изменить» / «Удалить» у оценки видны только её
  владельцу. Скрытие элементов интерфейса дополняет серверную проверку, но не
  заменяет её.
- **FR-007 (MUST). Отказ в доступе.** Ответ 403 отдаётся страницей с текстом на
  русском языке: заголовок «Недостаточно прав», пояснение «Изменять каталог
  может только администратор.» и ссылка «← На главную». Ответ 404 остаётся
  стандартным.
- **FR-008 (SHOULD). Отказ фиксируется в логе.** Каждый отказ по правам
  (403 при попытке изменить каталог и 404 при обращении к чужой оценке)
  пишется в логгер `brewery` уровнем `warning` с именем пользователя и путём
  запроса. Пароли, токены и содержимое форм в лог не попадают.
- **FR-009 (MUST). Без миграций данных.** Новых полей и таблиц не появляется;
  существующие пользователи сохраняют учётные записи, их роль определяется
  текущим значением `is_staff`.
- **FR-010 (MUST). Нет самоповышения.** Ни один веб-сценарий не позволяет
  пользователю выдать себе или другому пользователю `is_staff`; роль меняется
  только в `/admin/` (или management-командой).
- **FR-011 (MUST). Состав администраторов.** При выкате `is_staff = True`
  остаётся ровно у двух учётных записей — `admin` и `qqmax7`; у всех остальных
  пользователей `is_staff = False`. Требование фиксирует состояние на момент
  выката, а не запрет на новых администраторов: назначать и снимать `is_staff`
  по-прежнему можно в `/admin/`. Учётные записи не удаляются и не
  переименовываются — пользователи без `is_staff` продолжают работать с базой
  как читатели и авторы своих оценок. Если у `admin` или `qqmax7` не окажется
  `is_staff`, требование считается выполненным после выдачи роли этим двум
  аккаунтам.

## 6. UX и тексты

- Отказ 403 — отдельная страница: заголовок «Недостаточно прав», текст
  «Изменять каталог может только администратор.», ссылка «← На главную».
- Сообщения и подтверждения, которые уже есть, не меняются: «Это действие
  нельзя отменить.» на странице удаления, пустые состояния «Пока нет записей.»,
  «У вас пока нет оценок.».
- Кнопка «Добавить оценку» и ссылки «Оценить» / «Изменить оценку» остаются на
  месте для любого пользователя.
- Никаких новых значков роли в шапке не добавляется: имя пользователя и
  «Выйти» остаются как есть.
- Локаль `ru-ru`, десятичный разделитель — запятая; на новые тексты это не
  влияет.

## 7. Данные и миграции

- Схема базы данных не меняется, новых полей и таблиц нет, миграций нет.
- Роль определяется существующим `auth_user.is_staff`; права, выданные через
  группы и `has_perm`, не используются.
- Существующие данные (пиво, хмель, производители, оценки) не переписываются.
- Выкат включает разовую сверку ролей: `is_staff = True` остаётся только у
  `admin` и `qqmax7`, у всех остальных флаг снимается (FR-011). Сверка
  делается вручную в `/admin/` или одной management-командой; она меняет
  только `auth_user.is_staff`, не трогая пароли и прочие поля, и миграцией не
  является.
- Проверка перед рестартом: `manage.py shell -c "..."` должен показать ровно
  `['admin', 'qqmax7']`; тем, у кого флаг снят, сообщаем заранее, что каталог
  теперь доступен им только для чтения.

## 8. Краевые случаи и ошибки

- **Гость.** Любой защищённый раздел даёт 302 на вход с `next`; отказ 403 для
  гостя не используется, иначе он потеряет возможность войти и продолжить.
- **Пользователь без прав.** Читает каталог, ставит оценки, правит только свои;
  при попытке изменить каталог — 403; при обращении к чужой оценке — 404.
- **Администратор.** Правит каталог, но чужие оценки через веб-интерфейс ему
  тоже недоступны: это сохраняет симметрию с правилом приватности и не мешает
  работать через `/admin/`.
- **Оценка без владельца** (`owner IS NULL`, возможно для старых записей):
  недоступна через веб никому; на средние в списке пива и в отчёте продолжает
  влиять как раньше.
- **Прямой POST без CSRF-токена** отклоняется стандартным механизмом Django
  (403) — поведение не меняется.
- **Ни одной записи.** Пустые списки остаются как сейчас; у пользователя нет
  кнопок создания, поэтому пустое состояние не обещает действий.
- **Массовое удаление.** Администратор может удалить пиво с чужими оценками —
  каскад сохраняется; предупреждение ограничено существующим текстом.
- **Логи.** Фиксируются только имя пользователя, метод, путь и код ответа.

## 9. Нефункциональные требования

- Все проверки прав — на сервере, в представлениях; атрибуты HTML и скрытие
  кнопок не считаются защитой (конституция III).
- Дополнительных запросов к базе не появляется: `is_staff` берётся из уже
  загруженного `request.user`, владелец оценки — из `owner_id`.
- Новых зависимостей и изменений деплоя нет; совместимо с текущими gunicorn,
  WhiteNoise и SQLite.
- Логи — только в stdout/stderr через логгер `brewery`, без персональных данных
  сверх имени пользователя.
