# Spec-driven development в HopBeer

Spec-driven development (SDD) — это способ работы, при котором **спецификация
поведения пишется и согласуется до кода**, а код, миграции и тесты считаются её
реализацией. Спека здесь — не документ «для отчётности», а рабочая единица:
по ней планируют, по ней пишут тесты, по ней принимают результат.

Подход сознательно лёгкий: markdown-файлы в репозитории, без внешнего CLI,
без генерации кода и без обязательного сервера. Всё читается в git и в ревью.

## Что это меняет на практике

| Было | Стало |
|---|---|
| Задача сразу в коде | Сначала `spec.md`: что и зачем, критерии приёмки |
| «Сделал, вроде работает» | `AC-*` + тест на каждый критерий |
| Решения в переписке | Решения в `plan.md` и журнале спеки |
| Поведение восстанавливают по коду | Baseline-спека и история изменений |
| Ревью «по диффу» | Ревью спеки → плана → кода |

## Артефакты и каталоги

```
specs/
├── README.md            этот файл: процесс
├── constitution.md      принципы проекта (рамка решений)
├── backlog.md           очередь идей и известных долгов
├── templates/           шаблоны spec/plan/tasks/checklist
├── 000-baseline/        as-is спецификация текущего поведения
│   └── spec.md
├── NNN-<slug>/          спека изменения (папку создаёт new_spec.py)
    ├── spec.md          требования, критерии приёмки
    ├── plan.md          технический план
    ├── tasks.md         задачи с трассировкой на AC
    └── ...              при необходимости: research.md, contracts/, notes.md
```

- Одна спека — одна папка `NNN-<slug>`.
- `000` зарезервирован под baseline и не меняется задним числом: изменения
  поведения оформляются новой спекой.
- Номер новой спеки — максимальный существующий + 1 (скрипт делает это сам).
- Имена файлов фиксированы: `spec.md`, `plan.md`, `tasks.md`. Дополнительные
  файлы допустимы, если на них ссылается спека.

## Жизненный цикл

```
draft ──► review ──► approved ──► in-progress ──► implemented
  ▲          │            │            │
  └──────────┘            └────────────┴──► superseded (заменена другой спекой)
```

1. **draft.** Автор заполняет `spec.md`: проблема, цели, non-goals, `FR-*`,
   `AC-*`, влияние на baseline. Открытые вопросы перечислены явно.
2. **review.** Ревьюер проверяет по чек-листу: критерии наблюдаемы и
   однозначны, нет противоречий с конституцией и baseline, есть non-goals.
3. **approved.** Спека принята. Только теперь пишется `plan.md` и `tasks.md`;
   план не должен добавлять требований, которых нет в спеке.
4. **in-progress.** Задачи выполняются по порядку, чекбоксы в `tasks.md`
   закрываются только после проверки. Изменение требований — через журнал спеки.
5. **implemented.** Все `AC-*` покрыты тестами, тесты зелёные, изменения
   выкачены (или готовы к выкату), спека и код согласованы.

Если по ходу выясняется, что спека неверна, — она правится (с записью в журнал
изменений), а не игнорируется.

## Definition of Ready (спека готова к работе)

- [ ] Проблема и цель понятны человеку, не участвовавшему в обсуждении.
- [ ] Есть non-goals: что в эту спеку не входит.
- [ ] У каждого требования `FR-*` есть хотя бы один `AC-*`.
- [ ] Критерии приёмки проверяемы: Given/When/Then, без «удобно» и «красиво».
- [ ] Описано влияние на существующее поведение (`SPEC-000`).
- [ ] Нет открытых вопросов, блокирующих реализацию (остальные — с owners).
- [ ] Спека не противоречит `constitution.md`.

## Definition of Done (спека выполнена)

- [ ] Все задачи `T-*` закрыты и проверены.
- [ ] Каждый `AC-*` имеет тест (или зафиксированное «не покрыто» с причиной).
- [ ] `manage.py test` и `manage.py check` зелёные.
- [ ] Миграции созданы и применяются на чистой БД; потерь данных нет.
- [ ] Тексты интерфейса на русском, локаль `ru-ru` учтена.
- [ ] Эксплуатационные изменения отражены в `plan.md` и `docs/DEPLOYMENT.md`.
- [ ] Статус спеки — `implemented`, журнал изменений заполнен.
- [ ] Ревью кода ссылается на спеку и её AC.

## Трассируемость

Идентификаторы сквозные и стабильные:

| Префикс | Где | Смысл |
|---|---|---|
| `SPEC-NNN` | шапка спеки, коммиты, PR | спека целиком |
| `FR-NNN` | `spec.md` | функциональное требование |
| `AC-NNN` | `spec.md`, `tasks.md`, тесты | критерий приёмки |
| `T-NNN` | `tasks.md`, коммиты | задача реализации |

Тест ссылается на критерий в докстринге или имени класса, например:

```python
def test_beer_search_filters_by_name(self):
    """AC-004: поиск по названию возвращает только совпадающие записи."""
```

Имя теста описывает поведение, а не реализацию: `test_list_shows_own_rating_only`
лучше, чем `test_get_queryset_prefetch`.

## Как начать новую спеку

```powershell
.venv\Scripts\python.exe scripts/new_spec.py --title "Поиск и фильтры в списке пива"
```

Скрипт создаст `specs/001-poisk-i-filtry-v-spiske-piva/` с тремя файлами по
шаблонам и подставит `SPEC-001`, дату и владельца (по умолчанию — «не
назначен»). Проверить без создания папки: `--dry-run`. Дальше:

1. Заполните `spec.md`.
2. Прогоните его по чек-листу `templates/checklist.md`, отправьте на ревью.
3. После `approved` заполните `plan.md` и `tasks.md`.
4. Реализуйте, отмечайте `T-*`, обновляйте статус.

Вручную: скопируйте `specs/templates/*.md` в новую папку и замените
`{{SPEC_ID}}`, `{{TITLE}}`, `{{DATE}}`, `{{OWNER}}`.
## Brownfield: как перевести существующий проект

Проект уже написан, поэтому переход идёт не «с нуля», а ретроспективно:

1. **Baseline.** `specs/000-baseline/spec.md` описывает текущее поведение —
   включая то, что кажется очевидным. Это точка отсчёта и защита от регрессий.
2. **Разрывы.** Всё, что в коде расходится с желаемым поведением, вынесено в
   раздел «Известные расхождения» baseline и в `backlog.md` с номерами будущих
   спек. Разрыв не «лечится» молча — он становится задачей.
3. **Новые изменения — только по спекам.** Первая же доработка после перехода
   оформляется как `SPEC-NNN`, даже если кажется маленькой.
4. **Постепенное покрытие тестами.** У baseline не все AC покрыты тестами;
   приоритет — тем, что чаще ломаются или связаны с приватностью и правами.

## Дефекты и хотфиксы

- Дефект поведения: сначала тест, воспроизводящий его, затем исправление.
  Если поведение было описано в спеке — ссылка на нарушенный `AC-*`.
- Срочный хотфикс (прод недоступен, утечка данных) делается сразу, но спека
  или запись в журнале baseline оформляется в течение рабочего дня.
- Изменение требований «по факту» запрещено: сначала правится спека.

## Чек-лист ревью спеки

- [ ] Проблема сформулирована без решения «как делать».
- [ ] Требования не противоречат друг другу и baseline.
- [ ] Критерии приёмки проверяемы и не описывают реализацию.
- [ ] Учтены права доступа и приватность (см. `constitution.md` и разделы 2, 4.3 baseline).
- [ ] Учтены пустые состояния, ошибки и границы (0, 1, много).
- [ ] Non-goals явно перечислены.
- [ ] Понятно, как проверять: тесты, ручные шаги, данные.

## Связь с ИИ-агентами

`AGENTS.md` в корне обязывает агента читать конституцию и спеку до изменений и
не менять поведение без спеки. Шаблоны и baseline дают агенту контекст, которого
не хватает в диффе: зачем, для кого и что считается готовым.
